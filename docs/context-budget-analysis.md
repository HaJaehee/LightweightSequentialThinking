## 1. 배경 — 왜 지금 떠올랐나

v1.14.0에서 승인 대기를 45초 슬라이스로 쪼갰습니다. 클라이언트의 60초 리밋에 호출이
죽으면서 대화가 끊기는 문제를 없앤 건 맞지만, **도구 호출 횟수가 늘었습니다.** 5분 숙고면
슬라이스 11개, 15분이면 20개입니다.

호출이 늘어나자 원래도 있던 질문이 커졌습니다 — **매 응답이 전체 태스크 목록을 다시
싣는 게 맞는가?** `handlers.py`에서 `tasks=plan.tasks_brief()`가 37곳에 있고, 사실상 모든
응답이 전체 플랜을 재전송합니다.

이 설계 자체는 근거가 있습니다. 이 프로젝트의 전제가 *"약한 모델에게 기억을 요구하지
않는다"*이고, 매 응답의 `next_action` + 전체 상태가 그 전제를 구현합니다. 문제는 그 비용이
측정된 적이 없다는 것입니다.

## 2. 측정 방법 (재현 가능)

실제 코드(`responses.build`, `models.Task.brief`, `schemas.build_tool_definitions`)로
페이로드를 만들어 UTF-8 바이트를 셌습니다.

- **토큰 환산: `bytes // 3`.** 한국어는 BPE에서 대략 1.2~1.7자/토큰, JSON 뼈대는 ~4자/토큰.
  둘이 섞인 이 페이로드에서 중간값 추정입니다. **±30% 오차를 가정하십시오.**
  정확한 수치가 필요하면 대상 모델의 실제 토크나이저로 다시 재야 합니다.
- 시나리오: 태스크 5개, 한국어 제목, `min_result_log` 가드를 실제로 통과하는 길이의
  증거 기록(80~110자).
- "청구 토큰"은 프롬프트 캐싱이 **없다고** 가정하고 매 턴 히스토리 전체를 다시 읽는
  비용의 합(prefix sum의 합)입니다. 캐싱 유무는 §5에서 따로 다룹니다.

## 3. 발견 1 — 고정 오버헤드가 4,880 토큰

작업을 시작하기도 전에, **매 요청마다** 다음이 실려 나갑니다.

| 항목 | 토큰 |
|---|---:|
| `plan_and_think` 스키마 | 1,367 |
| `update_task_progress` 스키마 | 787 |
| `request_user_approval` 스키마 | 732 |
| `get_current_plan` 스키마 | 186 |
| **`tools/list` 합계** | **3,072** |
| `agents.md` 시스템 프롬프트 | 1,808 |
| **고정 오버헤드** | **4,880** |

이건 낭비가 아니라 **의도된 투자**입니다. Phase 1 블루프린트가 명시적으로 "약한 모델을
위해 모든 파라미터에 구체적 Example을 넣는다"고 정했고, E16·E17(테스트 매트릭스)은 이
장황함이 실제로 클라이언트 오류를 막았다고 기록합니다.

그래도 결과는 직시해야 합니다:

- **4k 컨텍스트 모델에서는 하네스가 시작조차 못 합니다.** 도구 정의만으로 창의 75%.
- **8k에서도 작업 여유가 3,300 토큰뿐입니다.**

사내 LLM의 실제 컨텍스트 창을 모르면 나머지 분석이 전부 공중에 뜹니다. **이게 §8의
1순위 확인 항목입니다.**

## 4. 발견 2 — 상태 재전송의 누적 (토큰 낭비)

### 한 응답의 구성

```
전체 응답                520 tok
echo 제거 시              90 tok
─────────────────────────────
echo 자체                430 tok   ← 응답의 82%
```

### 실행 단계 6회 호출(IN_PROGRESS 1 + DONE 5) 누적

```
누적 echo             2,782 tok
현재 사본 1개면          520 tok
─────────────────────────────
낡은 중복             2,262 tok   ← echo 예산의 81%
```

마지막 턴에 컨텍스트에는 태스크 목록 사본이 **6개** 있고, **5개가 틀린 상태**입니다.

### 증거 기록이 곱셈 인자

`Task.brief()`는 `result_log`를 자르지 않습니다. D18(v1.13.1)에서 **의도적으로** 캡을
제거했습니다 — 승인 페이지가 같은 dict로 만들어지는데, 증거가 `...`로 잘리면 사람이 검증할
수 없기 때문입니다. 그 판단은 옳았지만, 같은 dict가 매 턴 모델에게도 갑니다.

| 태스크 | 증거 길이 | echo 1회 | 전체 echo |
|---:|---:|---:|---:|
| 5 | 40자 | 562 | 3,372 |
| 5 | 120자 | 962 | 5,772 |
| 5 | 400자 | 2,362 | 14,172 |
| 8 | 120자 | 1,484 | 13,356 |
| 12 | 120자 | 2,183 | 28,379 |
| 12 | 400자 | 5,543 | **72,059** |

호출 수 ≈ 태스크 수이므로 **태스크에 대해 O(n²), 증거 길이에 대해 선형**입니다.
`max_tasks` 기본값이 12라는 점을 기억하십시오 — 위 표의 마지막 행은 기본 설정에서
도달 가능한 값입니다.

`models.py:172`의 주석이 이미 이 상황을 예견해 뒀습니다:

> *"증거가 컨텍스트를 위협하게 되면, 읽는 쪽이 아니라 **쓰는 쪽**에 캡을 걸어라
> (`min_result_log` 옆에 최대값을). 읽는 지점의 제한은 저장소가 가진 것과 조용히
> 어긋난다."*

### 분할 대기 슬라이스

v1.14.0이 추가한 비용입니다.

```
APPROVAL_PENDING 1개          240 tok   (태스크 목록 미포함 — 설계대로)
그중 next_action_hint         128 tok   ← 글자 하나 안 틀리고 반복
5분 숙고 = 11슬라이스        2,640 tok   = 작업 전체의 약 38%
15분 숙고 = 20슬라이스       4,800 tok
```

슬라이스가 태스크 목록을 싣지 않는 건 잘한 설계입니다(승인으로 오독될 표면 제거). 다만
128토큰짜리 동일 힌트를 11~20번 반복하는 건 순수 낭비입니다.

## 5. 발견 3 — 컨텍스트 창 포화

작업 종료 시점의 컨텍스트 점유(고정 오버헤드 4,880 포함, 승인 슬라이스 11개 포함):

| 태스크 | 증거 | peak | 4k | 8k | 16k | 32k |
|---:|---:|---:|:-:|:-:|:-:|:-:|
| 5 | 40자 | 10,802 | ✗ | ✗ | ○ | ○ |
| 5 | 120자 | 13,202 | ✗ | ✗ | ○ | ○ |
| 5 | 400자 | 21,602 | ✗ | ✗ | ✗ | ○ |
| 8 | 120자 | 20,285 | ✗ | ✗ | ✗ | ○ |
| 12 | 120자 | 34,314 | ✗ | ✗ | ✗ | ✗ |
| 12 | 400자 | 77,994 | ✗ | ✗ | ✗ | ✗ |

**포화의 결과가 조용하다는 게 진짜 위험입니다.** 창이 넘치면 호스트(AnythingLLM)가 보통
가장 오래된 메시지부터 자릅니다. 그러면 잘려나가는 것이 **시스템 프롬프트, 원래 목표,
승인받은 계획**입니다 — 즉 하네스가 존재하는 이유 전부입니다. 남는 건 최근 도구 결과들뿐이고,
모델은 규칙 없이 상태만 든 채로 계속합니다. 서버는 이걸 감지할 방법이 없습니다.

이건 D1과 같은 모양의 실패입니다. D1은 낡은 승인이 실행을 인가하는 문제를 **TTL**로 막았지만,
**컨텍스트에는 TTL이 없습니다.**

### 프롬프트 캐싱 여부가 크게 갈림

| | 누적 append | 청구 토큰 |
|---|---:|---:|
| 현재(echo 전체) | 2,782 | 9,127 |
| 증거 전면 제외 | 2,059 | 7,424 (−18%) |

- **vLLM/SGLang 등 automatic prefix caching이 있으면**: 재읽기가 거의 공짜라 "청구 토큰"
  열은 무의미해지고 append 열만 유효합니다.
- **없으면**: 청구 열이 그대로 발생합니다.
- **어느 쪽이든 창 포화(§5 표)는 동일하게 발생합니다.** 캐싱은 비용을 줄일 뿐 자리를
  만들어주지 않습니다.

## 6. 발견 4 — Lost in the Middle

LLM은 컨텍스트의 **처음과 끝**에 있는 정보를 잘 쓰고 **중간**에 있는 것을 놓칩니다
(Liu et al., *Lost in the Middle: How Language Models Use Long Contexts*, arXiv 2307.03172).
모델이 작을수록 심하고, 이 프로젝트의 대상은 정확히 그 작은 모델입니다.

### 현 설계가 잘 맞는 부분 (바꾸면 안 되는 것)

- **`next_action`이 항상 컨텍스트 맨 끝에 있습니다.** 가장 잘 주목받는 위치에 가장
  중요한 지시가 놓입니다. 우연이 아니라 "매 응답이 다음 행동을 말한다"는 설계의 결과입니다.
- 시스템 프롬프트가 맨 앞 — 차선의 위치.
- 최신 상태도 맨 끝. 낡은 사본은 중간으로 밀려나 상대적으로 덜 주목받습니다.

### 위험한 부분

**낡은 사본에는 낡은 데이터뿐 아니라 실행 가능한 낡은 지시문이 들어 있습니다.**
`state_machine.py:288`이 힌트에 리터럴 id를 박습니다:

```python
f"Call update_task_progress with task_id={task.task_id} and status='IN_PROGRESS'."
```

태스크 5를 하는 시점에도 히스토리에는 *task_id 1·2·3·4를 지시하는 문장 4개*가 살아 있습니다.
데이터가 아니라 **명령문**이고 전부 틀렸습니다. 모순은 부재보다 나쁩니다 — 모르는 모델은
묻지만, 답을 여러 개 본 모델은 하나를 고릅니다.

### ⚠ 반직관적 지점 — 증거를 다 빼면 오히려 악화됩니다

태스크 N은 흔히 태스크 N−1의 산출물을 필요로 합니다(위 예시: "추출한 매출 테이블"을
"증감률 산출"이 씁니다). 그 산출물이 처음 등장한 곳은 N−1의 DONE 응답이고, 그건 턴이
지나면서 **중간으로 가라앉습니다.**

지금은 echo가 매 턴 그걸 맨 끝으로 끌어올려 주고 있습니다. 즉 **echo가 lost-in-the-middle을
완화하는 역할을 겸하고 있습니다.**

그래서 "증거 전면 제외"는 나쁜 거래입니다:

| 방식 | 청구 토큰 | 절감 | lost-in-the-middle |
|---|---:|---:|---|
| 전체 (현재) | 9,127 | — | 완화됨 |
| **직전 태스크 증거만** | **8,143** | **−10%** | **유지** |
| 증거 전면 제외 | 7,424 | −18% | **악화** |

추가 8%를 얻자고 실제 태스크 간 의존성을 깨는 건 손해입니다. **§7-2가 이 판단의 근거입니다.**

## 7. 개선 제안

우선순위 순. 각각 독립적으로 적용 가능합니다.

### 제안 1 — `result_log`를 쓰는 쪽에서 캡 (효과 大 / 위험 小)

`min_result_log` 옆에 `max_result_log`(예: 300자)를 두고 `update_task_progress`가 받는
시점에 자릅니다. `models.py:172` 주석이 지시하는 바로 그 방식입니다.

- **장점**: 사람이 보는 것과 모델이 보는 것이 계속 일치합니다 — D18이 지킨 보장을
  깨지 않습니다. §4 표의 400자 행이 사라집니다.
- **단점**: 잘린 사실을 모델에게 알려야 합니다(안 그러면 재작업 때 자기 산출물이 잘린 걸
  모릅니다). 잘림 표시와 함께 "전문은 저장소에 있다"고 알리는 방식 검토 필요.
- **주의**: 자르는 게 아니라 **거부**하는 선택지도 있습니다("너무 길다, 요약해서 다시").
  약한 모델에게 재작성을 요구하는 건 실패율이 높으니 자르는 쪽이 안전할 것으로 보이나,
  실기 확인 필요.

### 제안 2 — 모델용 echo에서 오래된 증거만 제외 (효과 中 / 위험 小)

`Task.brief()`를 소비자별로 분리:

- `brief()` — 승인 페이지용. **지금 그대로.** 전체 증거 포함.
- `brief_for_model()` — **직전에 완료된 태스크의 `result_log`만** 유지, 그보다 오래된 것은
  제외. 재작업 대상의 `previous_result_log`는 항상 유지(REWORK_NOT_DONE 가드가 의존).

§6에서 설명한 대로, 전면 제외가 아니라 **직전 것만 유지**여야 합니다.

- **효과**: 청구 토큰 −10%, 증거가 길수록 커짐.
- **위험**: `handlers.py`에서 `tasks_brief()`가 페이지로 가는 경로와 모델로 가는 경로를
  정확히 갈라야 합니다. 잘못 섞으면 D18 회귀입니다. `_wait_for_human` → `open_request`
  경로가 페이지용임을 반드시 확인할 것.

### 제안 3 — 힌트에서 리터럴 `task_id` 제거 (효과 小 / 안정성 大)

`next_action_hint`에서 `task_id=3` 같은 리터럴을 빼고, 이미 존재하는 `next_task` 필드에만
둡니다. 힌트는 "`next_task`가 지정한 태스크를 처리하라"로 바꿉니다.

- **효과**: 토큰 절감은 거의 없습니다. **낡은 사본이 실행 가능한 명령문에서 단순 데이터로
  바뀝니다.** §6의 핵심 위험이 사라집니다.
- **위험**: 간접 참조는 약한 모델에게 더 어렵습니다. 지금의 직설적 힌트가 효과적인 이유가
  바로 직설적이기 때문일 수 있습니다. **이 제안은 §8의 A/B 없이는 적용하지 마십시오.**
  현재 힌트 문구는 D14·D19 대응 과정에서 다듬어진 것이라 함부로 건드릴 대상이 아닙니다.

### 제안 4 — 반복 슬라이스의 힌트 압축 (효과 中 / 위험 小)

2번째 이후 `APPROVAL_PENDING`은 짧은 힌트로 내립니다(모델이 직전 턴에 긴 버전을 이미 읽음).

```
1회차: 전체 힌트 (128 tok)
2회차~: "Not decided. Call request_user_approval ASK_USER again now. No text."
```

- **효과**: 11슬라이스 기준 약 1,000 토큰, 20슬라이스면 약 2,000.
- **위험**: 모델이 짧은 힌트를 무시하고 루프를 이탈할 수 있습니다. 다만 이탈해도
  APPROVAL_PENDING 가드(D20) 때문에 상태를 바꾸지는 못합니다 — 실패해도 토큰만 낭비됩니다.
- **대안**: `call_budget`을 60초 리밋에 더 붙여 슬라이스 수 자체를 줄이는 방법.
  다만 관측된 클라이언트 캡(`client_caps.json`)보다 위로 올리면 안 됩니다.

### 제안 5 — 도구 스키마 다이어트 (효과 大 / 위험 大)

`tools/list` 3,072 토큰이 매 요청에 실립니다. 특히 `plan_and_think` 1,367 토큰.

**권장하지 않습니다.** 이 장황함은 E16·E17에서 실제 클라이언트 오류를 막은 것으로
기록돼 있고, Phase 1이 명시적으로 선택한 설계입니다. 4k~8k 창이라는 게 **실측으로**
확인되고 다른 모든 수단을 쓴 뒤의 마지막 카드로만 검토하십시오.

### 제안 6 — 컨텍스트 포화 감지 (효과: 진단)

서버는 컨텍스트 사용량을 볼 수 없지만 **누적 응답 크기는 셀 수 있습니다.** 플랜별로
누적 바이트를 `audit.jsonl`에 남기고 임계치를 넘으면 경고하면, §5의 조용한 실패가
관측 가능해집니다. `get_current_plan`이 복구 도구로 이미 있으므로, 임계치 초과 시
"컨텍스트가 위험하다, 새 대화를 시작하고 `get_current_plan`으로 재동기화하라"는
안내를 낼 수도 있습니다.

## 8. 구현 전에 반드시 측정할 것

**이 문서의 어떤 제안도 실기 근거 없이 적용하지 마십시오.** v1.14.0에서 고친 버그가
정확히 이 유형이었습니다 — 문서화된 기본값(`resetTimeoutOnProgress`)을 확인 없이 믿고
안전 장치를 그 위에 세웠다가, 그 기본값이 반대였습니다(D21).

측정 순서:

1. **사내 LLM의 컨텍스트 창 크기.** 4k인지 32k인지에 따라 §5 표의 결론이 완전히 달라집니다.
   이걸 모르면 나머지는 의미가 없습니다.
2. **AnythingLLM이 창 초과 시 어떻게 자르는지.** 앞을 자르는지, 요약하는지, 그냥 실패하는지.
   앞을 자른다면 §5의 조용한 실패가 실재합니다.
3. **prefix caching 유무.** 추론 서버가 vLLM/SGLang 계열인지. §5의 "청구 토큰" 열이
   유효한지가 여기서 갈립니다.
4. **실제 토크나이저로 재측정.** 이 문서의 `bytes // 3`은 추정입니다.
5. **어느 쪽으로 먼저 깨지는지 관측.** 창 포화인지, 낡은 지시문 오독인지. 둘은 처방이
   다르고, 안 보고 고르면 또 하나의 추측 기반 최적화가 됩니다.

가장 싼 계측 경로는 **제안 6을 먼저 구현하는 것**입니다 — 코드 변경이 작고, 나머지
모든 판단의 근거를 만들어 줍니다.

## 부록 — 측정 재현

이 문서의 모든 수치는 저장소 코드로 직접 뽑았습니다. 재현 스크립트는 커밋하지 않았습니다
(일회성 분석 도구라 유지보수 부채가 됩니다). 필요하면 다음으로 다시 만들 수 있습니다:

**직렬화가 두 가지라는 점에 주의하십시오.** 도구 정의와 응답 페이로드는 다르게 인코딩되고,
같은 함수로 재면 표와 다른 숫자가 나옵니다.

- **응답 페이로드**: `protocol.py`가 `json.dumps(payload, ensure_ascii=False, indent=2)`로
  직렬화해 그대로 모델에게 보냅니다. 들여쓰기가 실제로 전송되므로 **`indent=2`로 재야
  합니다.**
- **도구 정의**: 클라이언트가 `tools/list` 결과를 받아 자기 형식으로 다시 직렬화해
  요청에 싣습니다. 보통 압축 형태이므로 **`indent` 없이 재는 쪽이 현실적입니다.**
  (`indent=2`로 재면 3,462가 나옵니다 — 표의 3,072과 차이 나는 이유입니다.)

```python
from planning.models import Plan, Task, PlanStatus, TaskStatus
from planning.responses import build
from planning.schemas import build_tool_definitions
import json

compact = lambda p: len(json.dumps(p, ensure_ascii=False).encode()) // 3
wire    = lambda p: len(json.dumps(p, ensure_ascii=False, indent=2).encode()) // 3

# 고정 오버헤드 — 클라이언트가 재직렬화하므로 압축 기준
print(sum(compact(t) for t in build_tool_definitions(auto_advance=True)))   # 3072

# echo 1회 — 서버가 보내는 그대로
p = Plan("p", "목표", plan_status=PlanStatus.IN_EXECUTION.value,
         tasks=[Task(1, "제목", TaskStatus.DONE.value, result_log="증거"*30)])
print(wire(build(p, tasks=p.tasks_brief(), progress=p.progress())))
```

"청구 토큰"은 프롬프트 캐싱이 없다고 가정한 prefix sum의 합입니다:

```python
def billed(seq):
    ctx = total = 0
    for x in seq:
        ctx += x        # 도구 결과가 히스토리에 추가됨
        total += ctx    # 다음 호출이 전체를 다시 읽음
    return total
```
